# Content plans and playbooks

Read this before calling any plan or playbook tool (`create_plan`, `update_plan`, `produce_plan`, `list_plans`, `get_plan`, `create_playbook`, `create_playbook_from_plans`, `instantiate_playbook`, `list_playbook_cycles`, `get_playbook_cycle`, `list_my_playbook_steps`, `complete_playbook_step`, `generate_cycle_content`, …): a content plan, the plans board, a launch calendar, or a reusable sequence of content to write.

---

## Content Plans & Playbooks

The **plans board** is Marcora's content pipeline: a queue of ideas/intents (**plans**) that move through stages and get *produced* into real Content. **Playbooks** are reusable, ordered templates of plan items you can stamp out as a batch.

> **Mindset:** a plan is *intent*, Content is *output*. Creating a plan doesn't write anything — `produce_plan` does. Keep the two straight: `create_content` writes or saves a document now; `create_plan` records "we should write X" for later.

### The plan stage machine

`Suggested → Accepted → In_Process → Complete`, plus `Dismissed` (terminal). Transitions go through `update_plan target_stage:` (use the UNDERSCORE form `In_Process`). Only these are allowed: Suggested→Accepted/Dismissed · Accepted→In_Process/Dismissed · In_Process→Complete/Accepted/Dismissed · Complete→Accepted (re-open, clears produced content)/Dismissed. **There is no `delete_plan`** — dismiss with `target_stage:"Dismissed"`.

The **starting stage is set automatically from `source`**, you don't control it directly: `cora_requested` / `playbook` → **Accepted** (actionable now); `user_added` / `cora_proactive` / `workflow` → **Suggested** (awaits user accept). Set `source:"cora_requested"` when the user explicitly asked; `source:"cora_proactive"` when you're surfacing an unprompted suggestion. **Never** pass `source:"workflow"` or `"playbook"` from an interactive session.

### Visibility

**Plans are `private` by default** — the creator's ideas queue, invisible to teammates (a teammate's private plans return NotFound and never appear in their `list_plans`). Assigning a plan to another member (`assigned_to`) **auto-promotes it to `team`** — assignment is a communication act, even over an explicit `private`. Only the plan's **creator** can change `visibility`; mention the change to the user before sending it. **Playbooks default to `team`;** `instantiate_playbook` **inherits** the playbook's visibility onto the plans it creates.

### The 5 plan tools

- **`create_plan`** — Create a plan. Only `title` is required. Optional executable params (`prompt`, `blueprint_id`, `project_id`, `category_id`, `due_date`, `reference_document_ids`, `context_collection_ids`, `targeting_dimension_ids`, `assigned_to`, `visibility`). **Dedupe first:** call `list_plans` with a `project_id` filter before creating; if a matching Accepted/Suggested plan exists, offer to `update_plan` it instead. When creating several in one turn, correlate them with `source_metadata.batch_id` and deep-link the filtered view.
- **`get_plan`** — Fetch one plan by `plan_uuid` with all linked params. **Always call before `update_plan`** to avoid overwriting with stale values. `_produced_content` null = no content yet.
- **`list_plans`** — Discovery + dedup. Results cover only the plans the user can see (an empty result ≠ the team has no plans). Useful filters: `stage` (single-value array, UNDERSCORE form), `project_id`, `assignee_scope` (`me` default | `created_by_me` | `all_visible`). Current limitations: `due_before`, `due_after` and `search_text` are accepted but not yet applied, and for `stage` and `source` only the first value is used — pass single-value arrays.
- **`update_plan`** — Partial update; only keys you send mutate. Construct a minimal diff after `get_plan`. `reference_document_ids` / `context_collection_ids` / `targeting_dimension_ids` are **full-replace** when non-empty; `[]` is ignored, so they can't be cleared. `reference_document_ids` keeps a step's existing plan links unless `builds_on_plan_ids` is sent or plan UUIDs are included; those must be EARLIER steps of the same playbook cycle — a plan's own UUID, a later step, a plan outside the cycle, or an unknown/other-team id is rejected, and `builds_on_plan_ids` (`[]`/`null` clears) follows the same rule. `null` clears `blueprint_id` / `due_date` but is ignored for `project_id` / `category_id`. Server-managed fields (`source`, `produced_content_id`, timestamps, etc.) are rejected as immutable.
- **`produce_plan`** — The MCP equivalent of the plans-board **Generate** button. Requires the plan in **Accepted** stage (Suggested → `update_plan target_stage:"Accepted"` first). **⚠️ Consumes Studio Credits and takes 1–5 min — confirm before producing a plan the user didn't explicitly ask to produce.** The plan's `prompt`, targeting, context collections, and project are used as generation inputs — set them via `update_plan` BEFORE producing.
  - **Both paths are ASYNC now** — the tool returns immediately with a `generation_id`; **poll `get_generation_status`**. A plan **with** a blueprint → `path:"blueprint"`; **without** a blueprint → `path:"freeform"`. On completion Marcora links the produced content and flips the plan to `In_Process` (then `Complete` when the content reaches ready).

### The 6 playbook tools

- **`list_playbooks`** — All playbooks visible to the caller (team + own private). Summaries only — call `get_playbook` for items. Use before `instantiate_playbook`/`update_playbook` to find the right id.
- **`get_playbook`** — One playbook with its full ordered item list. Inspect before instantiating/editing.
- **`create_playbook`** — Author a reusable template from scratch: `name` + optional ordered `items` (each item becomes one plan on instantiation). An item can carry `builds_on`: 0-based positions, in the same `items` array, of EARLIER items it builds on (never itself or a later one); each step's generation then draws on the steps it builds on. Defaults `visibility:"team"`. Optionally set **`anchor_date`** (`YYYY-MM-DD`) when the template is built around a real date — it persists on the playbook and becomes the default anchor at instantiation. Steps can be `kind` `content` (default), `checklist` (a to-do the owner ticks off) or `action` (a connected-app action: `slack/post_message`, `asana/create_task`, `gmail/create_draft`, with their `params`; the owner runs it in the app, not over MCP), with `optional`, `owner_user_id`, `reviewer` and `goes_out_offset_days`. The playbook can set `anchor_label`, `default_project_id` and `variables` (`{Name}` placeholders).
- **`create_playbook_from_plans`** — Capture existing plans as a template ("save what worked"): pass `plan_ids`; their title/description/prompt/blueprint/category copy into ordered items. Use this (vs `create_playbook`) when the user liked a batch they already ran.
- **`update_playbook`** — Rename/re-describe (patch in place) or restructure. If `items` is provided it **FULLY REPLACES** the items and their order; omit `items` to leave them. An id-matched item that omits `builds_on` keeps its links, remapped to the new positions: links to removed steps are dropped, and moving a step ahead of a step it still builds on is rejected unless you also send `builds_on` for it (a new list, or `[]` to clear). `visibility` change is creator-only. Pass **`anchor_date`** to set the reference date, or `null` to clear it. **Always `get_playbook` first and send every item you keep back with its `id`** (ids are re-issued on every save, so use the latest read): an item sent with its `id` keeps its step (kind, owner, reviewer, optional, second date, action), and a step field you send changes only that field. An id-less list that would reset checklist/action steps is refused with nothing written; send `kind` on every item to rewrite steps on purpose.
- **`instantiate_playbook`** — **Run** a playbook: create one Accepted plan per item, in order, as a batch (source `"playbook"`, inheriting the playbook's visibility). This is a distinct bulk action — it does NOT create/edit the playbook. Optional `project_id`, `assigned_to`, `category_id`, and **`anchor_date`**: each item's `offset_days` is applied to the anchor to compute that plan's due date (e.g. "instantiate my launch playbook anchored to next Monday"). If `anchor_date` is omitted, the playbook's persisted anchor is used. If the playbook has `variables`, pass their values in `variables`; if it has optional steps, ask the user which to leave out (`skip_item_ids`).

> **Playbook responses carry links — hand them to the user, not raw ids.** Every playbook read/write tool returns `anchor_date` (persisted `YYYY-MM-DD`, or `null`) and a **`link_url`** that opens the playbook in Marcora. `instantiate_playbook` returns the created **cycle** (`run`, with its own `link_url` → `app.marcora.ai/runs/{run_id}`) plus a `plans[]` array where **each plan has its own `link_url`** → `app.marcora.ai/plans/{plan_uuid}`. Share the cycle link to hand off the whole batch.

### Playbook cycles (the 8 cycle tools)

`instantiate_playbook` starts a **cycle**: one step (a plan) per playbook item. Pass `topic` (what the cycle is about, up to 4,000 characters) so the cycle's content is generated against it. The cycle's `run_id` and `link_url` come back in `run`. A step is a plan, identified by its `plan_uuid`.

- **`list_playbook_cycles`** — Running cycles (`status`: `active` default | `complete` | `all`; optional `playbook_id`), each with progress (done / total). Use it to find a `run_id`.
- **`get_playbook_cycle`** — One cycle with its steps in order: instructions (`prompt`), stage, due date, owner, the earlier steps it builds on, the produced document, and the recorded result once completed.
- **`list_my_playbook_steps`** — The open steps assigned to the user across all cycles, soonest due first. `due_by` (YYYY-MM-DD) includes overdue steps. This is the daily "what do I need to do" check. Then read the step in context with `get_playbook_cycle`.
- **`complete_playbook_step`** — Mark a step Complete with optional `result_url` and `note` as evidence. Works for steps with no document (which `update_plan` cannot complete). Needs edit rights on the step. Calling it again on an already-Complete step keeps its original `completed_at` / `completed_by`, but a newly supplied `result_url` or `note` overwrites the previously recorded one (omit them to leave the recorded result unchanged); only a checklist step can be undone, with `reopen_playbook_step`. A Dismissed step is refused. Only call it when the work was actually done.
- **`reopen_playbook_step`** — Untick a completed CHECKLIST step (back to Accepted, result cleared); other step kinds are refused.
- **`update_playbook_cycle`** — Rename a cycle (`name`) and/or change its `topic` (`null` or blank clears it). To change a step's title, prompt, due date or assignee, or to dismiss it, use `update_plan` with the step's `plan_uuid` from `get_playbook_cycle`.
- **`generate_cycle_content`** — "Generate all": starts generating the document for every step that has none, in order, on the server. **Consumes Studio Credits, one generation per step — confirm before starting.** Skips checklist and action steps, dismissed and already-generated steps, and teammates' steps (reported with a reason). One batch per cycle at a time; calling again while one runs returns `started: false`. Async.
- **`get_cycle_generation`** — Poll the latest batch (`running` / `completed` / `stopped` / `interrupted`) and each step's status. For one step's output use its `generation_id` with `get_generation_status`.
- To see every step of a cycle as plans, `list_plans` accepts `run_id` (combine with `assignee_scope: "all_visible"`); each plan row carries its `run_id`.

### Typical flows

- **Turn a suggestion into content:** `list_plans` (find it) → `update_plan target_stage:"Accepted"` → `produce_plan` → poll `get_generation_status` → hand the user the produced content's link.
- **Capture then reuse:** user runs a good batch of plans → `create_playbook_from_plans(plan_ids)` → later `instantiate_playbook(anchor_date=…)` to redeploy the sequence.
- **Author a template:** `create_playbook(name, items)` → `instantiate_playbook` when ready to deploy.
- **Run and follow a campaign:** `instantiate_playbook(playbook_id, anchor_date, topic)` → `generate_cycle_content(run_id)` (after confirming credits) → poll `get_cycle_generation` → `list_my_playbook_steps(due_by=today)` each day → `complete_playbook_step(plan_uuid, result_url)` as steps are done.
