# Content plans and playbooks

Read this before calling any plan or playbook tool (`create_plan`, `update_plan`, `produce_plan`, `list_plans`, `get_plan`, `create_playbook`, `create_playbook_from_plans`, `instantiate_playbook`, `list_playbook_cycles`, `get_playbook_cycle`, `list_my_playbook_steps`, `list_playbook_owner_names`, `add_playbook_step`, `update_playbook_step_status`, `generate_cycle_content`, …): a content plan, the plans board, a launch calendar, or a reusable sequence of content to write (`learn_marcora_tools({ page: "work-your-playbook-steps" })`).

---

## Content Plans & Playbooks

The **plans board** is Marcora's content pipeline: a queue of ideas/intents (**plans**) that move through stages and get *produced* into real Content. **Playbooks** are reusable, ordered templates of plan items you can stamp out as a batch.

> **Mindset:** a plan is *intent*, Content is *output*. Creating a plan doesn't write anything — `produce_plan` does. Keep the two straight: `create_content` writes or saves a document now; `create_plan` records "we should write X" for later.

### The plan stage machine

`Suggested → Accepted → In_Process → Complete`, plus `Dismissed` (terminal). Transitions go through `update_plan target_stage:` (use the UNDERSCORE form `In_Process`). Only these are allowed: Suggested→Accepted/Dismissed · Accepted→In_Process/Dismissed · In_Process→Complete/Accepted/Dismissed · Complete→Accepted (re-open, clears produced content)/Dismissed. **There is no `delete_plan`** — dismiss with `target_stage:"Dismissed"`.

The **starting stage is set automatically from `source`**, you don't control it directly: `cora_requested` / `playbook` → **Accepted** (actionable now); `user_added` / `cora_proactive` / `workflow` → **Suggested** (awaits user accept). Set `source:"cora_requested"` when the user explicitly asked; `source:"cora_proactive"` when you're surfacing an unprompted suggestion. **Never** pass `source:"workflow"` or `"playbook"` from an interactive session.

### Visibility

**Plans are `private` by default** — the creator's ideas queue, invisible to teammates (a teammate's private plans return NotFound and never appear in their `list_plans`). Assigning a plan to another member (`assigned_to`) **auto-promotes it to `team`** — assignment is a communication act, even over an explicit `private`. Only the plan's **creator** can change `visibility`; mention the change to the user before sending it. **Playbooks default to `team`;** `instantiate_playbook` **inherits** the playbook's visibility onto the plans it creates.

### The 5 plan tools

- **`create_plan`** — Create a plan. Only `title` is required. Optional executable params (`prompt`, `blueprint_id`, `project_id`, `category_id`, `due_date`, `draft_lead_days` [0–365 whole calendar days before `due_date`; stored lead only — MCP cannot enable auto-generate], `generation_settings` [`{ use_cycle_source?, calls_source? }`], `reference_document_ids`, `context_collection_ids`, `targeting_dimension_ids`, `assigned_to`, `visibility`). **Dedupe first:** call `list_plans` with a `project_id` filter before creating; if a matching Accepted/Suggested plan exists, offer to `update_plan` it instead. When creating several in one turn, correlate them with `source_metadata.batch_id` and deep-link the filtered view.
- **`get_plan`** — Fetch one plan by `plan_uuid` with all linked params (`blueprint_id` is integer or `null`, `draft_lead_days`, `generation_settings`, and for cycle steps `step.schedule` with `outcome`: `null` | `waiting_content` | `waiting` | `overdue` | `invalidated` | `cancelled` | `skipped` | `claimed` | `dispatching` | `started` | `failed` | `unknown`). **Always call before `update_plan`** to avoid overwriting with stale values. `_produced_content` null = no content yet.
- **`list_plans`** — Discovery + dedup. Results cover only the plans the user can see (an empty result ≠ the team has no plans). Filters: `stage` (single-value array, UNDERSCORE form), `source` (single-value array), `project_id`, `assignee_scope` (`me` default | `created_by_me` | `all_visible`), `due_before` (returns open plans strictly before that date, excluding `In_Process` / `Complete` / `Dismissed`).
- **`update_plan`** — Partial update; only keys you send mutate. Construct a minimal diff after `get_plan`. `context_collection_ids` and `targeting_dimension_ids` are **full-replace** (`[]` clears; `null` is ignored). `reference_document_ids` is full-replace when non-empty (`[]` is ignored) and keeps a step's existing plan links unless `builds_on_plan_ids` is sent or plan UUIDs are included; those must be EARLIER steps of the same playbook cycle — a plan's own UUID, a later step, a plan outside the cycle, or an unknown/other-team id is rejected with `InputError`, and `builds_on_plan_ids` (`[]`/`null` clears) follows the same rule. `prompt` replaces template text cleanly as plain text; `generation_settings` replaces the whole object (`null` clears). `null` clears `blueprint_id` / `due_date`, but is ignored for `project_id` / `category_id`; `draft_lead_days` (0–365) rejects `null`. Editing `draft_lead_days`, `schedule_time_zone`, `title`, `description`, `prompt`, `blueprint_id`, `project_id`, `reference_document_ids` (even `[]`), `builds_on_plan_ids` (when any link or ref doc remains), `context_collection_ids`, `targeting_dimension_ids`, `generation_settings`, non-null `owner_name`, `attach_content_id`, `assigned_to`, or moving to `Complete` / `Dismissed` turns auto-generate (`do_on_date`) off (MCP cannot turn it on). For playbook steps: `attach_content_id` attaches an existing document (`content_id`) as the step's output (content steps only; needs `replace_attached_content: true` if one is already attached; detach by moving back to `Accepted`), and `owner_name` (typed owner from `list_playbook_owner_names`, not for action steps), `due_time` (`"HH:MM"`, needs `due_date`) and `goes_out_time` (`"HH:MM"`, needs goes-out date) can be set or cleared with `null`. Server-managed fields (`source`, `produced_content_id`, timestamps, etc.) are rejected as immutable.
- **`produce_plan`** — The MCP equivalent of the plans-board **Generate** button. Requires an **Admin** or **Creator** role (Collaborators get `"Only Admins and Creators can create documents."`) and the plan in **Accepted** stage (Suggested → `update_plan target_stage:"Accepted"` first). **⚠️ Consumes Studio Credits and takes 1–5 min — confirm before producing a plan the user didn't explicitly ask to produce.** The plan's `prompt`, targeting, context collections, and project are used as generation inputs — set them via `update_plan` BEFORE producing.
  - **Both paths are ASYNC now** — the tool returns immediately with a `generation_id`; **poll `get_generation_status`**. A plan **with** a blueprint → `path:"blueprint"`; **without** a blueprint → `path:"freeform"`. On completion Marcora links the produced content and flips the plan to `In_Process` (then `Complete` when the content reaches ready).

### Playbooks & suggestions

- **`list_playbooks`** — All playbooks visible to the caller (team + own private). Summaries only — call `get_playbook` for items. Use before `instantiate_playbook`/`update_playbook` to find the right id.
- **`get_playbook`** — One playbook with its full ordered item list (content steps include `targeting_dimension_ids`, readable `context_collection_ids`, `use_cycle_source`, and `draft_lead_days`). Inspect before instantiating/editing.
- **`create_playbook`** — Author a reusable template from scratch: `name` + optional ordered `items` (each item becomes one plan on instantiation). An item can carry `builds_on`: 0-based positions, in the same `items` array, of EARLIER items it builds on (never itself or a later one); each step's generation then draws on the steps it builds on. Defaults `visibility:"team"`. Set `default_project_id` for runs in an existing project, or `new_project_each_use: true` (optionally with `project_name_pattern` supporting `{Variable}` tokens) to create a fresh project per run. Optionally set **`anchor_date`** (`YYYY-MM-DD`) when the template is built around a real date — it persists on the playbook and becomes the default anchor at instantiation. Steps can be `kind` `content` (default), `checklist` (a to-do the owner ticks off) or `action` (`action: { instruction }`, one or two plain sentences saying what to do, up to 12,000 characters, `{Variable}` allowed; there is no fixed list of actions or apps. When the step's owner presses Run in the Marcora app, their in-app agent carries it out using the owner's own connected apps, asks the owner for exact approval before EVERY write to a connected app or anything that reaches another person, and saves the result on the step. It does not run over MCP), with `optional`, `off_by_default` (starts unticked at instantiation; implies `optional`), `owner_user_id`, `owner_name` (typed owner up to 60 chars for content/checklist steps, matching `list_playbook_owner_names`), `due_time` (`"HH:MM"`, needs `offset_days`), `goes_out_offset_days`, `goes_out_time` (`"HH:MM"`, needs `goes_out_offset_days`), `targeting_dimension_ids`, `context_collection_ids`, `use_cycle_source`, and `draft_lead_days` (0–365). (`reviewer` is deprecated and ignored — not written or returned by MCP; existing values are kept.) The playbook can set `anchor_label`, `default_project_id`, and `variables` (`{Name}` placeholders).
- **`create_playbook_from_plans`** — Capture existing plans as a template ("save what worked"): pass `plan_ids`; their title/description/prompt/blueprint/category and content-step targeting/context defaults copy into ordered items. Use this (vs `create_playbook`) when the user liked a batch they already ran.
- **`update_playbook`** — Rename/re-describe/configure `new_project_each_use` & `project_name_pattern` (patch in place) or restructure. If `items` is provided it **FULLY REPLACES** the items and their order; omit `items` to leave them. An id-matched item that omits `builds_on` keeps its links, remapped to the new positions: links to removed steps are dropped, and moving a step ahead of a step it still builds on is rejected unless you also send `builds_on` for it (a new list, or `[]` to clear). `visibility` change is creator-only. Pass **`anchor_date`** to set the reference date, or `null` to clear it. **Always `get_playbook` first and send every item you keep back with its `id`** (ids are re-issued on every save, so use the latest read): an item sent with its `id` keeps omitted step fields (`kind`, `owner`, `owner_name`, `optional`, `off_by_default`, times, second date, `targeting_dimension_ids`, readable `context_collection_ids` plus hidden collections the caller cannot see, `use_cycle_source`, `draft_lead_days`, `action`), and a step field you send changes only that field (`reviewer` is deprecated and ignored). An id-less list that would reset checklist/action steps is refused with nothing written; send `kind` on every item to rewrite steps on purpose.
- **`instantiate_playbook`** — **Run** a playbook: create one Accepted plan per item, in order, as a batch (source `"playbook"`, inheriting the playbook's visibility). This is a distinct bulk action — it does NOT create/edit the playbook. Scope to `project_id` or `new_project: { name?, description? }` (mutually exclusive; `new_project_each_use: true` templates create one automatically if both are omitted). Optional `assigned_to`, `category_id`, **`anchor_date`** (omit to use the playbook's saved anchor; `null`/empty string for no anchor), `suggestion_id` (from `list_playbook_suggestions`), run-wide `targeting_dimension_ids` / `context_collection_ids` (beats template defaults for content steps; `[]` clears template defaults for the run), and **`step_overrides`** (`[{ item_id, owner?, prompt?, blueprint_id?, targeting_dimension_ids?, context_collection_ids? }]` — beats run-wide and template defaults; nothing is saved back to the template). Any step kind accepts `owner` (`{ user_id }` or `{ name }`; changing owner or setting typed `name` turns `do_on_date` off, while keeping the same member owner keeps it on); only content steps accept `prompt` (non-blank, `{Variable}` filled; blank refused), `blueprint_id` (UUID, integer, or `null`), `targeting_dimension_ids`, or `context_collection_ids` (passing content-only fields on checklist/action steps is refused). If the playbook has `variables`, pass their values in `variables`; if it has `optional` steps, ask which to leave out (`skip_item_ids`); if it has `off_by_default` steps, ask which to include (`include_item_ids`), because any not named are left out.
- **`list_playbook_suggestions`** — List call-detected playbook suggestions (`suggested` default | `started` | `dismissed` | `all`), with pre-filled `variables`, `anchor_date`, supporting quote, `coverage`, and matched `playbook`. Start one by passing `suggestion_id` to `instantiate_playbook`.
- **`dismiss_playbook_suggestion`** — Dismiss a call-detected playbook suggestion (`suggestion_id`), optionally saving a standing call-guidance rule (`instruction: { text }`, 1–300 chars) when the user explicitly asks to remember the preference for future calls. Already-started suggestions are refused (409).

> **Playbook responses carry links — hand them to the user, not raw ids.** Every playbook read/write tool returns `anchor_date` (persisted `YYYY-MM-DD`, or `null`) and a **`link_url`** that opens the playbook in Marcora. `instantiate_playbook` returns the created **cycle** (`run`, with its integer `id` / `run_id` for cycle tools, `project_id` / `project_name`, and its own `link_url` → `app.marcora.ai/runs/{playbook_run_uuid}`) plus a `plans[]` array where **each plan has its own `link_url`** → `app.marcora.ai/plans/{plan_uuid}`. Share the cycle link to hand off the whole batch.

> **Workflow steps (`kind: "workflow"`).** A playbook step can run one of the user's workflows once, on demand (`workflow: { workflow_id, inputs? }` in `create_playbook` / `update_playbook` items or `add_playbook_step`; pick from `list_playbook_workflow_options`). `get_playbook`, `create_playbook`, `update_playbook` and `create_playbook_from_plans` leave workflow steps out by default (and remap `builds_on`); pass `include_workflow_steps: true` to see them. **Before editing items with `update_playbook`, read with `include_workflow_steps: true` and send workflow steps back with their `id`s**: leaving one out is refused (409, nothing changed) unless you pass `include_workflow_steps: true` to remove it on purpose. Custom-workflow steps stay owned by the workflow's creator (`assigned_to` and `step_overrides.owner` can't change it; `owner_name` is rejected); `update_plan` / `update_playbook_step_status` Complete is a 409. ChatGPT never sees workflow steps or these four tools.

### Playbook cycles (the 13 cycle tools)

`instantiate_playbook` starts a **cycle**: one step (a plan) per playbook item. Pass `topic` (what the cycle is about, up to 4,000 characters) so the cycle's content is generated against it. The cycle's `run_id` and `link_url` come back in `run`. A step is a plan, identified by its `plan_uuid`.

- **`list_playbook_cycles`** — Running cycles (`status`: `active` default | `complete` | `all`; optional `playbook_id`), each with `playbook_name` (`"Deleted template"` if the source template was deleted), `project` (`project_id` / `project_name`), and progress (done / total). Use it to find a `run_id`.
- **`get_playbook_cycle`** — One cycle (`project_id` / `project_name`, `playbook_name: "Deleted template"` when deleted) with its steps in order (including steps added mid-cycle): instructions (`prompt`), stage, due date, owner (`assigned_to` and `step.owner_name`), `use_cycle_source`, `step.draft_lead_days`, `step.do_on_date`, `step.schedule_time_zone`, `step.schedule` (`outcome`: `null` | `waiting_content` | `waiting` | `overdue` | `invalidated` | `cancelled` | `skipped` | `claimed` | `dispatching` | `started` | `failed` | `unknown`), the earlier steps it builds on, the produced document, and the recorded result once completed.
- **`list_my_playbook_steps`** — The open steps assigned to the user across all running playbooks, soonest due first. `due_by` (YYYY-MM-DD) includes overdue steps. Pass `owner_name` (from `list_playbook_owner_names`, matched case-insensitively) to list open steps owned by a typed owner name instead (returns `due_time`, `owner_name`, `kind`). Read the step in context with `get_playbook_cycle`.
- **`list_playbook_owner_names`** — Alphabetical list of typed `owner_name` strings in use on the team's playbook steps (in first-used spelling). Call before setting `owner_name` or filtering `list_my_playbook_steps`.
- **`add_playbook_step`** — Add one step (`content` default, `checklist`, `action`, or `workflow` with `workflow: { workflow_id, inputs? }`) to a RUNNING playbook (`run_id`, `title`) without changing the template. Positions right after `after_plan_uuid`, or at the end; `builds_on` takes `plan_uuid`s of earlier steps in the cycle. Content steps support `prompt` (`{Variables}` filled), `blueprint_uuid`, `use_cycle_source`, `draft_lead_days` (0–365), `targeting_dimension_ids`, and `context_collection_ids` (step targeting/collections start empty unless passed — no cycle inheritance). Supports `owner_user_id` or `owner_name` (content/checklist only), `due_date` (deadline the step is due)/`due_time`, and `goes_out_date`/`goes_out_time` (`reviewer` is deprecated and ignored).
- **`update_playbook_step_status`** — (Workflow steps cannot be completed or reopened by hand: 409; run them with `run_playbook_step_workflow`.) Requires `action`: pass `action: "complete"` to mark a `content` or `checklist` step Complete with optional `result_url` and `note` as evidence (calling again on an already-Complete step keeps its original `completed_at` / `completed_by` while newly supplied `result_url` / `note` overwrite previous ones), or `action: "reopen"` to untick a completed CHECKLIST step (back to Accepted, result cleared; non-checklist steps refused). **Open `action` steps cannot be completed over external MCP** (always refused with `"Complete this action from its current Marcora conversation"`); action steps can only be completed inside a Marcora conversation (with both `result_url` and `note`). Works for steps with no document (which `update_plan` cannot complete); a Dismissed step is refused. Only mark Complete when the work was actually done.
- **`list_playbook_workflow_options`** — The workflows you can attach to a workflow step: your own `custom` workflows and team-shared `team_setup` workflows (with their declared `inputs`). Call it before creating or swapping a workflow step.
- **`get_playbook_step_workflow`** — Live state of a workflow step (`plan_uuid`): `status` (`idle` / `running` / `failed` / `done` / `unavailable`), input readiness, `can_run` with `blocked_reason`, `can_choose_another`, and the latest `run`. Present `link_url` as returned.
- **`run_playbook_step_workflow`** — Run the step's workflow once now (owner only). The step completes by itself when the run succeeds. 409 when already running, unavailable, missing inputs, or already ran. Never changes the workflow's own schedule.
- **`update_playbook_step_workflow`** — Swap the workflow and input mappings on an open workflow step (owner only), e.g. after the original was archived. 409 when the step is running or finished.
- **`update_playbook_cycle`** — Rename a cycle (`name`) and/or change its `topic` (`null` or blank clears it), returning the cycle including `project_id` / `project_name`. Targeting dimensions and context collections belong on individual content steps via `update_plan` and are **refused** here. To change a step's title, prompt, due date, targeting, or assignee, or to dismiss it, use `update_plan` with the step's `plan_uuid` from `get_playbook_cycle`.
- **`generate_cycle_content`** — "Generate all": starts generating the document for every open `content` step assigned to or created by the caller (including steps created by you that are assigned to a teammate), in order, on the server (Admin/Creator only). **Consumes Studio Credits, one generation per step — confirm before starting.** Skips checklist and action steps, dismissed and already-generated steps, and teammates' private or unowned steps (reported with a reason). One batch per cycle at a time; calling again while one runs returns `started: false`. Async.
- **`get_cycle_generation`** — Poll the latest batch (`running` / `completed` / `stopped` / `interrupted`) and each step's status. For one step's output use its `generation_id` with `get_generation_status`.
- To see every step of a cycle as plans, `list_plans` accepts `run_id` (combine with `assignee_scope: "all_visible"`); each plan row carries its `run_id`.

### Typical flows

- **Turn a suggestion into content:** `list_plans` (find it) → `update_plan target_stage:"Accepted"` → `produce_plan` → poll `get_generation_status` → hand the user the produced content's link.
- **Capture then reuse:** user runs a good batch of plans → `create_playbook_from_plans(team_id, plan_ids)` → later `instantiate_playbook(team_id, playbook_id, anchor_date=…)` to redeploy the sequence.
- **Author a template:** `create_playbook(team_id, name, items)` → `instantiate_playbook` when ready to deploy.
- **Run and follow a campaign:** `instantiate_playbook(team_id, playbook_id, anchor_date, topic)` → `generate_cycle_content(team_id, run_id)` (after confirming credits) → poll `get_cycle_generation(team_id, run_id)` → `list_my_playbook_steps(team_id, due_by=today)` each day → `update_playbook_step_status(team_id, plan_uuid, action="complete", result_url=…)` as steps are done.
